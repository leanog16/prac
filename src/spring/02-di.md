## Inversion of control

Without a framework, classes build their own collaborators:

```java
public class OrderService {
    private final PaymentClient payments = new StripePaymentClient("sk_live_...");   // hard-wired
}
```

That's hard to test (you can't swap in a fake) and hard to configure. With **dependency injection**, a class just **declares** what it needs, and the container supplies it:

```java
@Service
public class OrderService {
    private final PaymentClient payments;

    public OrderService(PaymentClient payments) {      // Spring passes an implementation in
        this.payments = payments;
    }
}
```

The objects Spring manages are **beans**, and the container that holds them is the **application context**. At startup Spring scans for components, works out the dependency graph, and creates every (singleton) bean in the right order. A missing or ambiguous dependency is a startup failure, not a runtime surprise.

## Declaring beans: stereotypes

| Annotation | Meaning |
|---|---|
| `@Component` | a generic Spring-managed class |
| `@Service` | business logic (a `@Component` with a clearer name) |
| `@Repository` | data access; also translates database exceptions into Spring's `DataAccessException` hierarchy |
| `@Controller` / `@RestController` | web layer; handles HTTP requests |
| `@Configuration` | a class that defines beans with `@Bean` methods |

## Constructor injection

```java
@Service
public class InvoiceService {
    private final InvoiceRepository invoices;
    private final Clock clock;

    public InvoiceService(InvoiceRepository invoices, Clock clock) {
        this.invoices = invoices;
        this.clock = clock;
    }
}
```

With a **single constructor**, `@Autowired` is optional; Spring uses it automatically. Prefer constructor injection:

- fields can be `final`, so the object is fully built and immutable,
- dependencies are explicit; a constructor with 9 parameters is a visible sign the class does too much,
- tests just call `new InvoiceService(fakeRepo, fixedClock)`, no Spring needed.

> [!warn] Field injection
> `@Autowired private InvoiceRepository invoices;` works but hides dependencies, prevents `final`, and makes plain unit tests impossible without reflection. Avoid it in application code (it's acceptable in test classes).

With Lombok, `@RequiredArgsConstructor` generates the constructor for all `final` fields.

## @Configuration and @Bean

You can't put `@Component` on classes you didn't write (a `Clock`, an `ObjectMapper`, an HTTP client). Define them in a configuration class instead:

```java
@Configuration
public class AppConfig {

    @Bean
    public Clock clock() {
        return Clock.systemUTC();
    }

    @Bean
    public RestClient githubClient(RestClient.Builder builder) {   // @Bean methods can take beans as parameters
        return builder.baseUrl("https://api.github.com").build();
    }
}
```

The method name becomes the bean name (`clock`, `githubClient`).

## Several implementations: @Primary and @Qualifier

```java
public interface Notifier { void send(String to, String msg); }

@Component("email") public class EmailNotifier implements Notifier { ... }
@Component("sms")   public class SmsNotifier implements Notifier { ... }
```

Injecting `Notifier` now fails at startup: *"expected single matching bean but found 2"*. Choose one of:

```java
@Primary                               // the default when nobody asks for a specific one
@Component("email")
public class EmailNotifier implements Notifier { ... }
```

```java
public AlertService(@Qualifier("sms") Notifier notifier) { ... }   // ask for a specific one
```

Or take them all: a `List<Notifier>` parameter receives every implementation, and a `Map<String, Notifier>` maps bean names to beans, which is handy for strategy patterns.

## Scopes

| Scope | Instances |
|---|---|
| `singleton` (default) | one per application context, shared by everyone |
| `prototype` | a new one every time it's injected or requested |
| `request` / `session` | one per HTTP request / HTTP session (web apps) |

Because singletons are shared across threads, **don't keep per-request state in fields** of a `@Service` or `@RestController`. Keep them stateless; put state in method variables, the database or a cache.

## Lifecycle hooks

```java
@Component
public class CacheWarmer {
    @PostConstruct
    void warm() { ... }          // after dependencies are injected

    @PreDestroy
    void flush() { ... }         // on graceful shutdown
}
```

To run something once the app has fully started, implement `CommandLineRunner` or `ApplicationRunner`, or listen for `ApplicationReadyEvent` with `@EventListener`.

## Conditional beans

Auto-configuration itself is built from conditions, and you can use the same ones:

```java
@Bean
@ConditionalOnProperty(name = "features.audit.enabled", havingValue = "true")
public AuditLogger auditLogger() { return new AuditLogger(); }

@Bean
@ConditionalOnMissingBean          // only if the app didn't define its own
public Clock clock() { return Clock.systemUTC(); }
```

`@Profile("dev")` on a bean or configuration class registers it only when that profile is active (more in the configuration lesson).

:::quiz
q: A class has one constructor taking two dependencies and no `@Autowired`. What does Spring do?
+ uses that constructor to inject both dependencies
- fails at startup: @Autowired is required
- creates the object with nulls
- injects only the first parameter
why: Since Spring 4.3, a single constructor is used for injection automatically.
:::

:::quiz
q: Two beans implement `PaymentGateway` and a service asks for one `PaymentGateway`. Without @Primary or @Qualifier…
- Spring picks one at random
- Spring picks the first one alphabetically
+ the application fails to start with NoUniqueBeanDefinitionException
- both are injected
why: Ambiguity is a startup error. Resolve it with @Primary, @Qualifier, or by injecting a List.
:::

:::quiz
q: What is the default bean scope?
+ singleton
- prototype
- request
- session
why: One shared instance per context, so beans must be thread-safe, which usually means stateless.
:::

:::quiz
q: Why use a `@Bean` method instead of `@Component`?
- @Bean beans are faster
+ to register objects from classes you can't annotate, such as library classes, or that need custom construction
- @Component is deprecated
- @Bean beans are always prototypes
why: @Bean lets you construct and configure third-party objects in code.
:::

---solution
package com.example.demo;

import java.util.List;
import org.springframework.stereotype.Service;

@Service
public class NotificationHub {

    private final List<Notifier> notifiers;

    public NotificationHub(List<Notifier> notifiers) {
        this.notifiers = notifiers;
    }

    public void broadcast(String to, String msg) {
        for (Notifier n : notifiers) {
            n.send(to, msg);
        }
    }
}

:::exercise
id: sd-stateful-bug
level: 3
title: Spot the concurrency bug
mode: answer
---
```java
@RestController
public class CartController {
    private List<String> items = new ArrayList<>();

    @PostMapping("/cart")
    public List<String> add(@RequestBody String item) {
        items.add(item);
        return items;
    }
}
```

Two different users each add one item. How many items does the **second** user's response contain?
---answer
2
---solution
2
---explain
The controller is a singleton shared by every request, so `items` is shared by all users (and `ArrayList` isn't even thread-safe). Keep beans stateless and store carts per user.
:::
