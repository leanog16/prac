## An instance, piece by piece

An **EC2 instance** is a virtual machine. Launching one means choosing:

| Choice | Example | Notes |
|---|---|---|
| **AMI** (Amazon Machine Image) | Amazon Linux 2023, Ubuntu 24.04, your own golden image | the OS disk template; region-specific IDs (`ami-0abc…`) |
| **Instance type** | `t3.micro`, `m7g.large`, `c7i.2xlarge` | family + generation + size; see below |
| **Network** | VPC, subnet (which AZ), public IP or not | next lesson |
| **Security groups** | `sg-web` | the instance firewall |
| **IAM role** | instance profile `app-runtime` | credentials for your code |
| **Storage** | 20 GiB gp3 root volume | EBS |
| **User data** | a bootstrap script | runs at first boot |

### Instance types

`m7g.large` reads as family **m** (general purpose), generation **7**, attribute **g** (Graviton, ARM), size **large**.

| Family | Optimized for |
|---|---|
| `t` | burstable, cheap: dev, small sites (CPU credits) |
| `m` | general purpose: balanced CPU/memory |
| `c` | compute: CPU-heavy work, batch, encoding |
| `r`, `x` | memory: caches, in-memory databases |
| `g`, `p`, `inf`, `trn` | GPUs and ML accelerators |
| `i`, `d` | local NVMe storage |

Attributes: `g` = Graviton (ARM, usually ~20% cheaper for the same performance), `i` = Intel, `a` = AMD, `n` = enhanced networking. Remember the multi-platform images from the Docker track: Graviton needs `linux/arm64` images.

## Security groups

A **security group** is a **stateful** firewall attached to an instance's network interface:

- Rules are **allow-only**; anything not allowed is denied.
- **Stateful**: if inbound traffic is allowed, the response goes out automatically (and vice versa).
- By default: no inbound allowed, all outbound allowed.
- A rule's source can be a CIDR (`203.0.113.0/24`) **or another security group**: "allow 5432 from `sg-app`" means "from any instance in sg-app", which survives IP changes and autoscaling.

```bash
aws ec2 authorize-security-group-ingress --group-id sg-0db \
  --protocol tcp --port 5432 --source-group sg-0app
```

> [!warn] 0.0.0.0/0 on port 22
> SSH open to the whole internet gets brute-forced within minutes. Don't open 22 at all: use **Systems Manager Session Manager** (`aws ssm start-session --target i-0abc…`), which needs no inbound port, no SSH keys, and logs every session. If you must use SSH, restrict it to your IP or a bastion's security group.

## Bootstrapping with user data

**User data** is a script that runs as root on the **first boot**:

```bash title=user-data.sh
#!/bin/bash
set -euxo pipefail
dnf install -y docker
systemctl enable --now docker
docker run -d --restart unless-stopped -p 80:8000 ghcr.io/acme/api:1.4.2
```

Its output is logged to `/var/log/cloud-init-output.log`. For anything non-trivial, bake a **golden AMI** with the software preinstalled (EC2 Image Builder, Packer). Instances then boot fast and identically.

## Storage: EBS and instance store

- **EBS** (Elastic Block Store) volumes are network-attached disks that **persist** independently of the instance, in one AZ. Types: `gp3` (general SSD, the default choice: set IOPS and throughput independently), `io2` (high-IOPS databases), `st1`/`sc1` (cheap HDD throughput).
- **Snapshots** are incremental, regional backups of EBS volumes in S3; copy them across regions for disaster recovery. Automate them with **Data Lifecycle Manager** or **AWS Backup**.
- **Instance store** is local NVMe on the host: very fast, but **lost** when the instance stops. Use it for caches and scratch only.
- Enable **EBS encryption by default** in each region.

## Instance metadata and IMDSv2

From inside an instance, `http://169.254.169.254/latest/meta-data/` returns its ID, AZ, IP, and the **temporary credentials** of its role. That makes it a target: an SSRF bug in your app could be tricked into fetching it. **IMDSv2** requires a session token obtained with a `PUT` request, which most SSRF attacks can't do:

```bash
TOKEN=$(curl -s -X PUT http://169.254.169.254/latest/api/token \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 300")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/placement/availability-zone
```

Require IMDSv2 on every instance (`HttpTokens=required`); it's the default for new instance types and in launch templates you control.

## Launching from the CLI

```bash
aws ec2 run-instances \
  --image-id ami-0abcdef1234567890 \
  --instance-type t3.small \
  --subnet-id subnet-0aaa \
  --security-group-ids sg-0web \
  --iam-instance-profile Name=app-runtime \
  --user-data file://user-data.sh \
  --metadata-options HttpTokens=required \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=web-1},{Key=Environment,Value=dev}]'
```

## Scaling: launch templates, Auto Scaling groups, load balancers

A single instance is a single point of failure. The standard pattern:

1. A **launch template** captures the instance configuration (AMI, type, SG, role, user data).
2. An **Auto Scaling group (ASG)** keeps N instances running across several AZs, replaces unhealthy ones, and scales between min and max:
   - **target tracking**: "keep average CPU at 50%";
   - **scheduled**: "10 instances on weekdays 08:00–18:00";
   - **step/predictive** policies for more control.
3. An **Application Load Balancer (ALB)** spreads HTTP(S) traffic across the ASG's instances, terminates TLS (with a free ACM certificate), health-checks targets, and routes by host or path (`/api/*` → API target group).

| Load balancer | Layer | Use |
|---|---|---|
| **ALB** | 7 (HTTP/HTTPS, gRPC, WebSocket) | web apps and APIs, path/host routing |
| **NLB** | 4 (TCP/UDP/TLS) | extreme throughput, static IPs, non-HTTP protocols |
| **GWLB** | 3 | third-party network appliances |

Treat instances as **cattle**: anything that must survive goes to EBS snapshots, S3, RDS, or the AMI, never only on one instance's disk.

## Paying for EC2

| Model | Discount | Commitment | Good for |
|---|---|---|---|
| **On-Demand** | none | none | spiky, short-lived, unknown workloads |
| **Savings Plans** | up to ~70% | $/hour for 1 or 3 years | steady baseline usage |
| **Reserved Instances** | up to ~70% | specific type/region, 1 or 3 years | older alternative to Savings Plans |
| **Spot** | up to ~90% | none, but AWS can reclaim with **2 minutes' notice** | fault-tolerant, stateless work: CI runners, batch, ASG capacity on top of a baseline |

Stopped instances don't bill compute, but their EBS volumes (and any unattached Elastic IPs) still cost money.

- open port 22 to 0.0.0.0/0
+ Systems Manager Session Manager, with no inbound ports
- telnet
- a public IP with password auth
why: Session Manager needs no inbound rules or SSH keys, and it's audited.
:::

:::quiz
q: What happens to data on an **instance store** volume when the instance is stopped?
- it's snapshotted automatically
+ it's lost
- it's moved to EBS
- nothing
why: Instance store lives on the physical host and doesn't survive stop/terminate.
:::

:::quiz
q: Which purchasing option fits a nightly batch job that can be interrupted and retried?
- On-Demand
- a 3-year Savings Plan
+ Spot instances
- Dedicated Hosts
why: Spot is the cheapest option, and interruptible work tolerates reclamation.
:::

:::quiz
q: What does IMDSv2 protect against?
+ SSRF attacks stealing role credentials from the metadata service
- DDoS attacks
- SQL injection
- unencrypted EBS volumes
why: The PUT-based session token defeats most server-side request forgery.
:::
